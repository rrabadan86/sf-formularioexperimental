1

Antes de começar

!

Nunca copie o disco da sua VPS para a do cliente

Parece atalho, mas leva junto o que não pode ir para outra loja: a sessão do seu WhatsApp (o robô do cliente entraria no seu número), o seu .env com as suas senhas, e logs/filas/cache que só dão problema. O caminho certo é sempre: clonar do GitHub → instalar com o script → escanear os QRs da loja.

O que ter em mãos

  • ✓A ficha da unidade preenchida (o cliente envia pelo /cadastro): EVO, grupo da equipe, professoras, endereço e contatos.
  • ✓Uma VPS Ubuntu com acesso SSH (IP + senha/chave). Duas lojas na mesma VPS pedem 8 GB.
  • ✓Dois números de WhatsApp: o do robô (o do Studio) e o da SoFIA (exclusivo dela), com alguém do lado do cliente para escanear os QRs.
  • ✓Do EVO da unidade: o tenant e o branch (na URL: …/app/<tenant>/<branch>/…), o DNS + Secret Key da API de integração e um usuário do site só para o robô (e-mail + senha).
  • ✓A chave da IA (Anthropic) para a SoFIA — é o que tem custo por conversa.
O que fica rodando em cada loja (troque <slug> pelo apelido, ex.: marista)
<slug>-painelO painel do Studio (login, mensagens, SoFIA, Slim Club…). Reiniciar não derruba o WhatsApp.
<slug>-expO robô: agenda e dispara os envios e mantém o WhatsApp do Studio conectado.
<slug>-sofiaA SoFIA (atendente com IA), com o WhatsApp dela.
<slug>-formO formulário de aula experimental, em https://SEU-PAINEL/agendamentoexperimental.
PastasCódigo em ~/SF-Chat_Experimental-Mensagens · formulário em ~/sf-form-<slug> · dados da SoFIA em ~/sofia-data-<slug> · o que é editado no painel fica em Experimental/data/ (fora do Git, com backup diário).
2

Instalar uma loja

Um comando (--tudo) instala o sistema, clona o formulário, gera os .env com segredos novos, pergunta as credenciais, sobe os 4 processos e liga o HTTPS. Os passos abaixo são tudo o que você faz à mão.

2.1 Preparar o servidor (fuso de Brasília)

Faça antes de instalar: o pm2 guarda o fuso de quando sobe. Se o fuso for ajustado depois, os horários do log ficam 3 h adiantados (aconteceu no Guará).

VPS · root
ssh root@IP-DO-CLIENTE
timedatectl set-timezone America/Sao_Paulo
date                                   # tem que mostrar o horário de Brasília (-03)
apt update && apt install -y git curl

2.2 Clonar o código

VPS
cd ~ && git clone https://github.com/rrabadan86/SF-Chat_Experimental-Mensagens.git
cd SF-Chat_Experimental-Mensagens/Experimental

2.3 Instalar tudo num comando (--tudo)

--tudo
bash setup-novo-studio.sh --tudo \
  --slug marista --studio "Studio SlimFit Marista" \
  --install-deps \
  --evo-tenant slimfit --evo-branch 22 \
  --port 8080 \
  --domain painel-marista.duckdns.org \
  --evo-email LOGIN-DO-ROBO-NO-EVO
  • ✓--slug: apelido curto, minúsculo, sem espaço/acento. Vira o nome dos processos (marista-exp…) e das pastas.
  • ✓--evo-tenant e --evo-branch: da URL do EVO da loja. Sem eles o robô cai no padrão do Setor Bueno (slimfit/15) e lê a loja errada.
  • ✓O que você não passar por flag (DNS/Secret Key do EVO, senha do robô, chave da IA, grupo da equipe) o script pergunta — senha e chaves ficam ocultas. Pode deixar em branco e preencher depois no painel: SoFIA → Configuração → 🔑 Credenciais da unidade.
  • ✓No fim ele imprime a senha do painel (usuário admin) e o IPv4 da VPS. Anote os dois. Para rever a senha: grep ^PAINEL_SENHA= .env.
⚠️ Nunca use < > nos valores (no terminal são redirecionamento): --evo-branch 22, nunca --evo-branch <22>. O script se atualiza sozinho pelo Git antes de instalar (--no-git-pull desliga).

2.4 Apontar o domínio (DuckDNS)

O painel precisa de um endereço para o HTTPS. O DuckDNS dá um grátis (algo.duckdns.org):

  1. Entre em duckdns.org (Sign in com Google), crie o subdomínio (ex.: painel-marista) e guarde o token do topo da página.
  2. No campo current ip, cole o IPv4 da VPS (o que o script imprimiu, ou curl -s4 ifconfig.me rodado na VPS) e clique em update ip.
  3. Confira na VPS: getent hosts painel-marista.duckdns.org tem que mostrar o mesmo IP. Em 1–2 min o https:// abre com cadeado.
As portas 80 e 443 precisam estar abertas também no firewall do provedor da VPS. Não clique em “update ip” sem preencher o campo: ele grava o IP do seu computador. Para o IP se manter certo sozinho, veja “Domínio que se atualiza sozinho” em Recursos opcionais.

2.5 Conectar os 2 WhatsApps e salvar no reboot

No painel (https://painel-marista.duckdns.org), aba 💬 WhatsApp, aparece o QR do robô; na aba 🤖 SoFIA, o QR dela. Escaneie cada um com o celular do número certo: WhatsApp → Aparelhos conectados → Conectar um aparelho. Depois:

VPS · uma vez por servidor
pm2 save
pm2 startup        # rode a linha que ele imprimir: sobe tudo sozinho após reboot
Escaneie uma vez só e deixe o robô quieto por algumas horas. Muitas tentativas seguidas fazem o WhatsApp bloquear novas conexões por algumas horas (“Não foi possível conectar o dispositivo”). Se o QR não pegar, use Conectar por código na mesma tela. A linha do robô precisa estar dentro do grupo da equipe.

2.6 IDs da aula experimental no EVO

VPS
bash setup-novo-studio.sh --slug marista --evo-tenant slimfit --evo-branch 22 --evo-ids

Ele lista as atividades e os serviços do EVO. Ache a atividade SlimFit e o serviço “Aula experimental” e grave os ids nos dois .env (EVO_ACTIVITY_ID e EVO_SERVICE_ID): Experimental/.env e ~/sf-form-marista/.env. Depois: pm2 restart marista-form marista-exp. Se já souber os ids, dá para passar --evo-activity-id/--evo-service-id no --tudo.

Não confunda os dois acessos ao EVO: DNS + Secret Key (EVO_DNS/EVO_TOKEN) são a API de integração; o e-mail/senha (EVO_EMAIL/EVO_PASSWORD) são o login do site, usado pelo robô para ler grade, faltas e segmentações.
3

Configurar antes de divulgar

A instalação deixa tudo rodando, mas com textos-modelo e sem o que depende da unidade. Faça os itens abaixo antes de divulgar para as alunas.

!

Os textos vêm com marcadores [ENTRE COLCHETES]

Se ninguém preencher, a aluna recebe colchetes no lugar do endereço e dos contatos. São três lugares: 🤖 SoFIA → Configuração (roteiro: [ENDEREÇO DA UNIDADE], [LINK DO FORMULÁRIO], [VALOR DE ENTRADA]… e as imagens de grade/preços), 💬 WhatsApp → Configuração (confirmação, follow-up, aniversário, renovação…) e o .env do formulário (abaixo).

  • ✓Identidade do formulário — em ~/sf-form-<slug>/.env: FORM_UNIDADE, FORM_ENDERECO, FORM_MAPS_URL, FORM_WHATSAPP (só dígitos, com 55), ZEE_STUDIO_PHONE (recepção) e PAINEL_URL. Sem eles a página mostra os dados do Setor Bueno. Depois: pm2 restart <slug>-form.
  • ✓Segmento do EVO para renovações — em Clientes → Segmentação do EVO, crie um segmento com nome contendo “Vencimento de Contrato Seman” (ex.: Vencimento de Contrato Semanal, igual ao do Bueno) e o filtro “Vencimento do contrato”. A renovação (todo dia, 14:30, direto para as alunas) e os contratos a vencer no mês (dia 28, no grupo da equipe) dependem dele: sem o segmento os dois falham. Teste com node src/renovacoes-mes-grupo.js --dry.
  • ✓2FA do EVO — se o usuário do robô tem verificação em duas etapas, siga “2FA do EVO” em Recursos opcionais. Sem isso, os jobs param com Waiting failed: 30000ms.
  • ✓Grupos do WhatsApp — confira o nome do grupo da equipe (e do Circuito, se houver) em 💬 WhatsApp → Configuração → 👥 Grupos, e que a linha do robô está nesses grupos.
  • ✓Usuários — em 👤 Perfis, crie um usuário para cada pessoa da recepção e marque só as telas que ela usa (inclusive 🤝 Slim Club, se for usar).
  • ✓Tags de alunas — ligue SoFIA → Tags → “Alunas / Ex-alunas automáticas”. Ela marca 0. Aluna/0. Ex Aluna pelo EVO uma vez por dia; a SoFIA, o Slim Club e as campanhas dependem dessas tags.
  • ✓Alertas no celular — o dono instala o app ntfy e assina o tópico do NTFY_TOPIC (está no Experimental/.env). Teste: curl -d "teste de alerta" ntfy.sh/SEU_TOPICO.
  • ✓Vigia — o backup diário já vem agendado; o vigia (avisa se o robô ou o painel caírem) entra no crontab -e (confira os caminhos com which node e which pm2):
    PATH=/usr/local/bin:/usr/bin:/bin
    */5 * * * * cd ~/SF-Chat_Experimental-Mensagens/Experimental && /usr/bin/node src/watchdog.js >> logs/watchdog.log 2>&1
    Teste: node src/watchdog.js deve dizer “✅ tudo ok”.
  • ✓Áudios das professoras (se usar o pós-aula) — copie os .ogg para Experimental/audios/ e ligue cada professora ao arquivo no AUDIO_MAP do .env (nome como aparece no EVO, minúsculo): AUDIO_MAP={"ana":"A-Ana-Pos"}. Reiniciar <slug>-exp.
4

Testar sem enviar

Cada job aceita um modo seguro: lê o EVO, escolhe quem receberia e monta o texto, mas não envia. Rode um de cada vez, com o robô parado, para não disputarem o navegador do EVO (a SoFIA e o painel continuam no ar).

testar os jobs (não envia)
cd ~/SF-Chat_Experimental-Mensagens/Experimental
pm2 stop SEU-SLUG-exp        # janela de teste

node src/enviar_confirmacoes.js --dry                    # confirmação da experimental
xvfb-run -a node src/followup-experimental.js --dry      # follow-up
xvfb-run -a node src/follow-up-no-show.js --dry          # faltas (no-show)
xvfb-run -a node src/aniversariantes.js                  # aniversário aluna (simulação)
xvfb-run -a node src/aniversario-ex.js                   # aniversário ex-alunas (simulação)
xvfb-run -a node src/aniversariantes-mes-grupo.js --dry  # equipe: aniversários do mês
xvfb-run -a node src/renovacoes-mes-grupo.js --dry       # equipe: contratos a vencer no mês
xvfb-run -a node src/renovar-contratos.js                # renovação (simulação)
xvfb-run -a node src/comparecimento.js --dry             # presença / troca de tags
xvfb-run -a node src/enviar-circuito.js --convocacao --dry # circuito
xvfb-run -a node src/ausentes-10-dias.js --dry           # ausentes 10 dias
xvfb-run -a node src/planilha-aniversarios.js --dry      # planilha + tags automáticas de alunas
xvfb-run -a node src/inadimplentes.js                    # cobrança: só LÊ os débitos
node src/free-antecedencia.js --dry                      # planos FREE: só lista

pm2 start SEU-SLUG-exp       # volta ao normal
Cada job termina com 🧪 Modo --dry: NADA foi enviado (ou “simulação”). Erro de login do EVO → confira EVO_EMAIL/EVO_PASSWORD e o 2FA. suspensoes.js mexe em contratos no EVO (não manda mensagem) — trate à parte. Para disparar um job de verdade com o robô ligado, use o “rodar job agora” de Atualizar e manter.
5

🏢 Duas lojas no mesmo servidor

Dois Studios do mesmo dono podem dividir uma VPS. A loja 2 é uma instalação completa e nova, num clone separado, com --slug, --port e --domain próprios. Nada é reaproveitado da loja 1. O que pesa é o navegador do WhatsApp (2 lojas = 4 WhatsApps): use 8 GB e o swap do passo B.

A Instalar a loja 2 com o --tudo

Troque lagosul2 pelo apelido, NN pelo branch do EVO da loja 2 e o subdomínio pelo seu.

VPS · loja 2
# 1) Clone SEPARADO — repare no nome da pasta ao final
cd ~ && git clone https://github.com/rrabadan86/SF-Chat_Experimental-Mensagens.git slimfit-lagosul2
cd slimfit-lagosul2/Experimental

# 2) Instala a loja 2 inteira. SEM --install-deps (o servidor já tem tudo da loja 1)
bash setup-novo-studio.sh --tudo \
  --slug lagosul2 --studio "Studio SlimFit Lago Sul 2" \
  --evo-tenant slimfit --evo-branch NN \
  --port 8081 \
  --domain painel-lagosul2.duckdns.org \
  --evo-email LOGIN-DO-ROBO-NO-EVO

# 3) Escalonar a loja 2 (no .env DA LOJA 2) para as duas não baterem no EVO juntas
nano .env
#    FORM_SLOTS_MINUTO=15            ← grade da loja 2 em :15 e :45 (loja 1: :00 e :30)
#    GRADE_FIXAS_CRON=47 5 * * *     ← grade fixa da loja 2 às 05:47 (loja 1: 05:40)
pm2 restart lagosul2-exp

# 4) DNS da loja 2 → o MESMO IPv4 da VPS · 5) QRs da loja 2 no painel dela · depois:
pm2 save

O script cuida sozinho do resto da loja 2: processos lagosul2-*, formulário em ~/sf-form-lagosul2 na porta do painel + 10 (8091), dados da SoFIA, tokens e tópico de alertas próprios, bloco do HTTPS acrescentado no Caddy (sem mexer no da loja 1) e backup diário próprio. Depois, faça na loja 2 a seção Configurar antes de divulgar inteira — inclusive os IDs do EVO e o segmento de renovações no EVO da loja 2.

⚠️ Portas: loja 1 = 8080 (painel) e 8090 (formulário); loja 2 = 8081 e 8091. Não use --port 8090 na loja 2 — bate com o formulário da loja 1.
⚠️ FORM_SLOTS_MINUTO é 15, não 30: o robô envia a grade no minuto escolhido e 30 min depois. Com loja 1 = 0 e loja 2 = 30, as duas mandariam juntas em :00 e :30 e estourariam o limite de 40 pedidos/min do EVO (a grade some das duas).

B Swap (uma vez só, no servidor)

Uma reserva de memória para os picos — não é por loja:

VPS · uma vez
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' | tee -a /etc/fstab     # mantém após reboot
free -h                                                  # confere a linha "Swap"

C Desencontrar os horários dos envios

No painel da loja 2 (💬 WhatsApp → Configuração), deixe os envios alguns minutos depois dos da loja 1 — ex.: loja 1 confirma às 08:30, loja 2 às 08:40. Vale para confirmações, follow-ups, faltas e resumo. A ANTHROPIC_API_KEY pode ser a mesma nas duas lojas (o Custo IA é medido por painel).

6

Atualizar e manter

A regra de ouro: o que reiniciar

<slug>-painelTelas do painel e páginas públicas (Slim Club, cadastro). Reinicie à vontade: o WhatsApp não cai.
<slug>-expO robô e o WhatsApp do Studio. Só reinicie quando a mudança for no robô (jobs, envios) e fora dos horários de envio — ele reconecta sozinho, mas é o momento em que a sessão pode cair.
<slug>-sofiaA SoFIA e o WhatsApp dela. Mesmo cuidado do robô.
<slug>-formO formulário. Reiniciar não afeta os WhatsApps.

Cada atualização diz quais processos reiniciar (veja o histórico). Na dúvida, reinicie só o painel e, se precisar, o robô depois, com calma.

6.1 Atualizar uma loja

VPS · atualizar
# código (sempre pela main — todas as lojas atualizam por ela)
cd ~/SF-Chat_Experimental-Mensagens && git fetch origin main && git reset --hard FETCH_HEAD
pm2 restart SEU-SLUG-painel                  # + SEU-SLUG-exp / -sofia se a atualização pedir

# formulário (repositório próprio)
cd ~/sf-form-SEU-SLUG && git fetch origin main && git reset --hard FETCH_HEAD
pm2 restart SEU-SLUG-form                    # páginas de texto (manual, implantação) nem precisam
O reset --hard só mexe no código: o que foi editado no painel (data/), os .env e as sessões do WhatsApp ficam intactos (estão fora do Git). Se uma atualização trouxer dependência nova, ela avisa para rodar npm install na pasta Experimental.

6.2 Rodar um job agora (com o robô ligado)

Para reenviar algo que falhou, sem parar o robô nem abrir um segundo WhatsApp: grave o pedido e o robô roda na hora.

VPS
cd ~/SF-Chat_Experimental-Mensagens/Experimental
echo '{"job":"aniversariantes"}' > data/rodar-job.json
pm2 logs SEU-SLUG-exp --lines 0                 # acompanhe; Ctrl+C para sair (não para o robô)

# contratos a vencer de um mês específico:
echo '{"job":"renovacoesMesGrupo","mes":11}' > data/rodar-job.json

Chaves: confirmacaoHoje, confirmacaoAmanha, followupMorning, followupAfternoon, noShowMorning, noShowAfternoon, aniversariantes, aniversarioEx, renovacao, renovacoesMesGrupo, resumoDia, ausentes, planilha, inadimplentes, freeAntecedencia. Se outro job estiver rodando, ele espera e tenta de novo a cada 30 s.

6.3 Acompanhar

  • ✓No painel: 💬 WhatsApp → Log mostra o que saiu no dia e as execuções que falharam (⚠️ “nada enviado”); a página Saúde mostra WhatsApp, EVO/2FA, disco e último backup.
  • ✓No servidor: pm2 status (tudo online) e pm2 logs SEU-SLUG-exp --lines 100.
  • ✓Backup: diário às 03:10, em Experimental/backups/ (últimas 14 cópias de data/). Teste manual: node src/backup-dados.js.
7

Quando algo dá errado

Os casos que já aconteceram em loja de verdade, com o diagnóstico e a solução. Toque para abrir.

📵 O WhatsApp do robô caiu e pede QR

Reconectar: no painel, aba 💬 WhatsApp, escaneie o QR uma vez só. Antes, no celular, desconecte os aparelhos antigos em Aparelhos conectados.

  • “Não foi possível conectar o dispositivo. Tente novamente mais tarde.” — bloqueio temporário do WhatsApp por excesso de tentativas. Pare de tentar por 2–3 horas e não reinicie o robô; depois escaneie uma vez.
  • QR não lê: use Conectar por código na mesma tela (código de 8 letras em Aparelhos conectados → Conectar com número de telefone). O código também aparece em pm2 logs SEU-SLUG-exp.
  • No log aparece Desconectado: LOGOUT — o WhatsApp encerrou a sessão: o aparelho foi removido no celular ou o número foi aberto em outro lugar ao mesmo tempo. Use um número dedicado ao robô.

Cai a cada reinício? O pm2 está matando o robô antes de ele salvar a sessão. Confira:

VPS
pm2 describe SEU-SLUG-exp | grep -i "kill"      # tem que ser 15000

Se não for 15000, recrie o processo (vai pedir QR uma última vez — faça com o celular por perto):

VPS
cd ~/SF-Chat_Experimental-Mensagens/Experimental
pm2 delete SEU-SLUG-exp && pm2 start ./scheduler-vps.sh --name SEU-SLUG-exp --interpreter bash --time --kill-timeout 15000 && pm2 save
🤖 A SoFIA pede QR ou travou em “Iniciando…”

Quase sempre pm2 restart SEU-SLUG-sofia resolve. Se insistir, limpe só o login dela (conversas, tags e roteiro não são tocados) e escaneie de novo:

VPS
pm2 stop SEU-SLUG-sofia
rm -rf ~/sofia-data-SEU-SLUG/.wwebjs_auth ~/sofia-data-SEU-SLUG/.wwebjs_cache
pm2 start SEU-SLUG-sofia
🔐 Job falhou com Waiting failed: 30000ms (login do EVO)
  • 2FA: o EVO pediu código. Configure o autenticador (2FA do EVO); quando o código vem por e-mail, o painel mostra o campo 🔐 Código do EVO em 💬 WhatsApp → Configuração.
  • Senha trocada ou conta travada por tentativas: atualize em SoFIA → Configuração → 🔑 Credenciais da unidade e destrave a conta no EVO.
  • Para reenviar depois de corrigir: rodar um job agora.
📄 Renovação ou “contratos a vencer” não saiu (ou veio vazio)
  • “Menu da Segmentação não encontrado” — falta o segmento “Vencimento de Contrato Semanal” no EVO da loja (ou foi renomeado). Veja Configurar antes de divulgar.
  • “Não consegui aplicar o período no filtro do EVO” — o filtro não apareceu nas 3 tentativas. A tela fica salva em data/renovacoes-mes-debug.png / renovacao-debug.png. Reenvie com {"job":"renovacoesMesGrupo","mes":11}.
VPS · o que aconteceu
grep -h "Contratos a vencer no EVO\|Filtro de período\|não encontrad\|contrato(s) a vencer" ~/.pm2/logs/SEU-SLUG-exp-out*.log | tail -8
🌐 O painel não abre ou fica “não seguro”
  • DNS: getent hosts SEU-DOMINIO tem que dar o IPv4 da VPS. Errado? Corrija o current ip no DuckDNS (cuidado: curl ifconfig.me às vezes devolve IPv6 — use curl -s4).
  • Portas: 80 e 443 abertas no firewall do provedor. ss -tlnp | grep -E ':80 |:443 ' tem que mostrar o caddy.
  • Certificado: journalctl -u caddy -n 50 --no-pager | grep -iE "certificate|challenge|error".
📅 O formulário fica em “Preparando os horários…”

A grade vem do EVO. Confira EVO_BRANCH_ID/EVO_SERVICE_ID no .env do formulário (o modelo vem com 128, que é do Bueno) e se a unidade tem a grade da experimental cadastrada no EVO. Teste: cd Experimental/src/agendamento_evo && python3 push_slots.py — 0 horários = falta grade no EVO. Duas lojas na mesma conta do EVO? Confira o FORM_SLOTS_MINUTO (loja 2 = 15).

🕒 O horário do log está 3 horas adiantado

O fuso foi ajustado depois de o pm2 subir. Os envios saem na hora certa (os agendamentos usam o fuso de Brasília); só o log fica errado. Corrija num momento calmo, porque reinicia todos os processos:

VPS
timedatectl set-timezone America/Sao_Paulo && date
pm2 save && pm2 update
🔁 O painel manda reiniciar o processo de outra loja (slimfit-exp)

Falta PM2_SLUG=SEU-SLUG no Experimental/.env (instalações pelo script já têm). Acrescente e rode pm2 restart SEU-SLUG-painel --update-env.

🤝 Aluna não consegue entrar no Slim Club

O Slim Club confere o telefone nos contatos com a tag 0. Aluna (ou 0. Equipe), que vem do EVO. Se o EVO tem um telefone antigo ou o mesmo número em várias alunas (o da loja, por exemplo), ela não entra — ou entra a pessoa errada. Corrija o celular no cadastro dela no EVO (aba Cadastro, todos os campos de telefone). Na sincronização seguinte (ou com {"job":"planilha"}) ela passa a entrar.

8

Recursos opcionais

Só ligue o que a loja for usar.

🔐 2FA do EVO (verificação em duas etapas)

Use um usuário do EVO só do robô, com e-mail próprio.

Principal — autenticador (TOTP), resolve sozinho, inclusive de madrugada. No cadastro do 2FA desse usuário, o EVO mostra um QR com uma chave secreta (base32). Capture a chave num app autenticador (2FAS ou Aegis) e cole no Experimental/.env: EVO_TOTP_SECRET=XXXXXXXX…. Depois: pm2 restart SEU-SLUG-exp --update-env. A chave é um segredo: nunca em chat, e-mail ou site de “ler QR”.

Reserva — código pelo painel. Quando o EVO manda o código por e-mail, o robô avisa no celular e mostra o campo 🔐 Código do EVO (2FA) em 💬 WhatsApp → Configuração; alguém digita o código ali. Com o TOTP configurado, essa reserva já vem ligada (sem TOTP: EVO_2FA_PAINEL=true). Espera padrão: 4 min (EVO_2FA_ESPERA_MS).

Resultado: a tag aparece na conversa e no filtro, sem contato duplicado. A grade cheia é consequência da metodologia — nada foi perdido.
  • 🐢 Grade de horários mais leve no EVO (só git pull no VPS): o cálculo/envio da grade ao formulário passou de “a cada 10 min, 24h” para a cada 60 min (07h–21h) e a cada ~3h de madrugada — boa prática da API do EVO. A grade vale 4h no formulário e a vaga é revalidada ao vivo no agendamento, então a aluna não vê “sem horário” por isso.
  • 🩹 Auto-recuperação da grade após reinício (só git pull + reiniciar <slug>-exp): se o formulário reinicia (deploy/queda) a grade enviada pode sumir — antes o formulário podia ficar até 60 min mostrando “sem horário” / “está demorando mais que o normal”. Agora o VPS confere a grade a cada 2 min e a reenvia na hora se ela sumiu, derrubando essa janela para ~2 min sem ninguém precisar rodar nada.
  • 🏷️ Renomear o servidor sem travar (só git pull + reiniciar): dá para trocar o nome do host da VPS (ex.: sf.gyn.bueno, sf.bsb.asa-sul) para identificar cada unidade. O Chromium guarda uma trava (SingletonLock) com o nome antigo da máquina e, ao renomear, recusava abrir (robô/SoFIA presos em “Iniciando…”). Agora SoFIA, robô, EVO e Instagram limpam essa trava sozinhos no boot — renomear virou seguro, sem reescanear QR. Útil ao provisionar cada unidade nova.
  • 🔗 Fim dos contatos duplicados pelo 9º dígito (só git pull + reiniciar a SoFIA): o mesmo número aparecia como dois contatos nas Conversas — um com o 9 (ex.: 61 99222-0710) e outro sem (61 9222-0710), porque o WhatsApp às vezes usa a forma antiga e o cadastro/EVO a nova. Agora a SoFIA reconhece as duas formas como a mesma pessoa: funde os cards já duplicados (no boot e a cada 3h) e faz toda mensagem nova cair no card certo, sem criar outro. Junta as mensagens em ordem e mantém as tags. (O CRM de Contatos já tratava isso.)
  • 🔐 2FA do EVO em TODOS os logins (só git pull + reiniciar): quando o MFA do EVO está ligado, todos os jobs que leem o EVO (confirmações, aniversariantes, ausentes, renovações, planilha, suspensões, circuito…) preenchem o código do autenticador sozinhos. Antes só o login das confirmações tratava o 2FA — os jobs de Segmentação travavam com Waiting failed: 30000ms. Sem EVO_TOTP_SECRET é no-op (unidade sem MFA segue igual). Ver Fase 2.5.
  • 📌 WhatsApp não cai mais no pm2 restart (instalação): o --kill-timeout 15000 nos processos dá tempo do Chromium fechar e gravar a sessão antes do pm2 encerrar (o padrão de 1,6s cortava no meio e pedia QR a cada restart). Loja nova já nasce com isso; em unidade antiga, recrie o processo com --kill-timeout 15000.
  • 🚫 Desligar envios por unidade (.env): JOBS_OFF=presentes,circuito_convocacao,circuito_lembrete faz o robô não agendar esses jobs e o painel (WhatsApp → Configuração) mostrar uma caixa "Envios desativados nesta unidade". Chaves: presentes · circuito_convocacao · circuito_lembrete (ou circuito = os dois).
  • 📅 Antecedência da renovação configurável (.env): o aviso de renovação sai por padrão 7 dias antes do vencimento; para mudar por unidade, defina RENOVACAO_DIAS_ANTES=30 (ex.: o Lago Sul avisa 30 dias antes). Usa o mesmo segmento do EVO (que busca pelo mês), só troca o "+7" pelo número do .env. Reiniciar exp.
  • 🏷️ Novas variáveis nas mensagens (reiniciar exp + painel e recarregar o navegador): a mensagem de renovação aceita {contrato} (nome do plano da aluna, ex.: COPA SLIM 2026 - C.C. - GRUPO 1) e os follow-ups aceitam {nome} (primeiro nome da aluna). O aniversário nos grupos também aceita {nome} (primeiro nome em texto normal) além do {aluna} (a @menção que marca a pessoa) — ex.: "Hoje é aniversário da {nome} {aluna}!"; no preview/teste o {aluna} aparece como @Maria para representar a marcação. As tags aparecem em WhatsApp → Mensagens ao editar cada texto.
  • 🎟️ Aula experimental vai até a última vaga real (só git pull + reiniciar exp; formulário: git pull + reiniciar <slug>-form no VPS): foi removida a regra que reservava as últimas vagas da turma (o antigo teto FORM_MAX_OCUPACAO). Agora, se a turma tem vaga de verdade (matriculadas < capacidade), a experimental pode marcar — não importa se a capacidade é 8, 9 ou 10. Vale para SoFIA, Cadastro Express e formulário. Turma cheia continua sem aparecer. O limite de nº de experimentais por turma (EVO_MAX_EXPERIMENTAIS, painel: Máx. experimentais por turma) segue valendo.
  • 🧾 Log com a mensagem inteira (reiniciar painel): no WhatsApp → Log ("Envios de hoje"), cada linha ganhou um "＋ ver tudo" que abre o texto completo enviado (antes mostrava só os primeiros ~80 caracteres). Usa <details> nativo (sem JS). Vale para os novos envios a partir da atualização.
  • 🩺 Saúde do sistema mais completa (reiniciar painel): a página Saúde agora também mostra o EVO / 2FA (se o autenticador está configurado ou se há código pendente para você digitar), a grade no formulário (se a versão do VPS está publicada), e um card Servidor com disco livre e último backup — tudo com semáforo 🟢🟡🔴.
  • ⏱️ Escalonar o envio da grade (2 lojas no mesmo VPS) (.env, reiniciar exp): FORM_SLOTS_MINUTO define o minuto em que a unidade empurra a grade ao formulário. Com duas lojas na mesma conta EVO, use minutos diferentes (loja 1 = 0 → envia em :00/:30; loja 2 = 15 → :15/:45 — não use 30, que cai nos mesmos minutos da loja 1) para não estourarem juntas o limite de 40 req/min do EVO — que fazia a grade sumir das duas. Também escalona o push do boot e a verificação inicial. Além disso, o POST da grade agora espera 60s (aguenta o cold start do formulário free).
  • 🖼️ Pré-visualização com o flyer (reiniciar painel): ao clicar em Pré-visualizar numa mensagem com foto e "Enviar com foto" marcado, o painel mostra o flyer junto do texto — igual a aluna vai receber.
  • 🗄️ Backup agendado na instalação (script): o setup-novo-studio.sh --start agora agenda o backup diário dos dados (03:10) no cron e roda um backup inicial — nenhuma unidade nova nasce sem cópia de segurança. É por unidade (marca # sf-backup:<slug>), então duas lojas no mesmo VPS convivem. A página Saúde → Servidor mostra o último backup.
  • 📅 Cadastro Express funciona sem a SoFIA (reiniciar painel): antes, o Cadastro Express dependia do processo da SoFIA para agendar no EVO (era a SoFIA que tirava o pedido da fila) — em unidade sem SoFIA ele ficava "processando" para sempre. Agora o próprio painel agenda, fazendo a mesma chamada do formulário (/api/book-sofia). Funciona igual ao formulário, sem SoFIA, IA ou QR. Onde a SoFIA está ligada (ex.: Bueno), convive normalmente — a captura da fila é atômica, então nunca agenda em dobro. O painel lê o SOFIA_TOKEN/URL do ChatBot/.env automaticamente.
  • ▶️ Re-rodar um job sob demanda (sem SSH complicado): grave data/rodar-job.json com {"job":"CHAVE"} e o robô já conectado roda na hora (sem abrir 2º WhatsApp). Chaves: aniversariantes, aniversarioEx, ausentes, renovacao, renovacoesMesGrupo, planilha, resumoDia, confirmacaoHoje, confirmacaoAmanha, followupMorning, followupAfternoon, noShowMorning, noShowAfternoon. Ex.: echo '{"job":"aniversariantes"}' > data/rodar-job.json.
  • 🏢 Multiunidade sem herdar nada do "Bueno" (só git pull): os processos PM2 vêm de PM2_SLUG (<slug>-exp/painel/sofia), o branch do EVO é derivado do .env de cada unidade (nada de slimfit/15 fixo), o SHEETS_ID não tem mais padrão (sem ID → planilha desligada) e o watchdog vigia os processos da própria unidade. O Setor Bueno segue idêntico (mantém os padrões legados quando não há PM2_SLUG).
  • 🤖 SoFIA usa o Chromium do sistema (instalação): o ChatBot/.env agora define CHROMIUM_PATH — sem isso a SoFIA caía no Chromium empacotado do puppeteer, que quebra por falta de libs (libnspr4.so → Code: 127) e entrava em loop de reconexão.
Para entender por dentro

O que o --tudo faz

Não precisa repetir à mão — fica aqui para quem quiser entender ou diagnosticar.

  1. Atualiza o próprio código pelo Git (git pull --ff-only).
  2. Com --install-deps: instala Node 20, pm2, tsx, Xvfb, Chromium e Python.
  3. Instala as dependências do robô (Experimental) e da SoFIA (ChatBot).
  4. Clona o formulário em ~/sf-form-<slug> e cria o ambiente Python dele.
  5. Gera os três .env (robô, SoFIA, formulário) com segredos novos e os tokens que ligam um ao outro; nunca sobrescreve um .env que já exista.
  6. Pergunta as credenciais que faltam e confere tudo (--check).
  7. Sobe os 4 processos no pm2 — robô e SoFIA com --kill-timeout 15000, para salvarem a sessão do WhatsApp ao reiniciar.
  8. Instala o Caddy, se faltar, e escreve o bloco do domínio no /etc/caddy/Caddyfile (painel + formulário em /agendamentoexperimental) e recarrega o Caddy.
  9. Agenda o backup diário e gera o primeiro.
As fases também rodam separadas, se precisar refazer uma: --check (só confere os .env), --start --domain … (sobe os processos e o HTTPS), --evo-ids. Ajuda completa: bash setup-novo-studio.sh --help.
