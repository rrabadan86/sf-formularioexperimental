Robô · instalação

Runbook de instalação

Passo a passo para colocar o robô rodando na franquia nova — do servidor zerado até tudo no ar, usando os comandos já validados em produção. Faça depois de receber a ficha da unidade preenchida.

Ubuntu + Node 20 PM2 24/7 Xvfb (tela virtual) ≈ 1 dia de trabalho
!

Nunca copie o disco da sua VPS para a do cliente

Parece atalho, mas arrasta três coisas que não podem ir para outra unidade:

  • 🚨 A sessão do seu WhatsApp — o robô do cliente conectaria no seu número (e ele sumiria da sua VPS).
  • 🔑 O seu .env com as senhas do seu EVO, seus alertas e sua planilha.
  • 🗑️ Logs, filas de mensagens, cache do navegador e node_modules — só dão problema.

O caminho certo: clonar do GitHub → criar um .env novo → escanear o QR do WhatsApp dele → testar. Sempre na versão mais atual do código.

Antes de começar

O que ter em mãos

  • ✓A ficha da unidade preenchida (o cliente envia pelo /cadastro): EVO, grupo, planilha, professoras, dados da unidade, alertas.
  • ✓O servidor (VPS) contratado pelo cliente — Ubuntu, com o acesso SSH (IP + senha/chave) em mãos.
  • ✓A linha de WhatsApp do Studio disponível para escanear o QR (com alguém do lado do cliente para confirmar no celular).
  • ✓Os áudios das professoras e a chave da conta de serviço do Google (se for usar planilha).
Fase 1

Preparar o servidor

1.1 Acessar, ajustar fuso e atualizar

Conecte no servidor do cliente por SSH e deixe tudo em dia. O fuso de Brasília mantém os horários dos jobs certos.

no seu PC → servidor do cliente
# conecte no servidor (troque pelo IP do cliente)
ssh root@IP-DO-CLIENTE

# fuso de Brasília + atualizações + git
timedatectl set-timezone America/Sao_Paulo
apt update && apt upgrade -y
apt install -y git

1.2 Node 20 + ferramentas de build

servidor
curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt install -y nodejs build-essential python3
node -v   # deve mostrar v20.x

1.3 Tela virtual (Xvfb) + bibliotecas do navegador

O EVO (Angular) é instável em modo headless puro. A configuração validada roda com tela virtual (Xvfb). Instale o Xvfb e as libs do Chromium.

servidor
apt install -y xvfb \
  ca-certificates fonts-liberation libasound2t64 libatk-bridge2.0-0t64 \
  libatk1.0-0t64 libc6 libcairo2 libcups2t64 libdbus-1-3 libexpat1 \
  libfontconfig1 libgbm1 libglib2.0-0t64 libgtk-3-0t64 libnspr4 libnss3 \
  libpango-1.0-0 libx11-6 libxcomposite1 libxdamage1 libxext6 libxfixes3 \
  libxrandr2 libxkbcommon0 xdg-utils wget
Ubuntu mais antigo? Se algum pacote com sufixo t64 não for encontrado, instale a versão sem o sufixo (ex.: libasound2). Os nomes variam por versão do Ubuntu.
Fase 2

Instalar o robô

2.1 Clonar o código e instalar dependências

servidor
cd ~
git clone https://github.com/rrabadan86/SF-Chat_Experimental-Mensagens.git
cd SF-Chat_Experimental-Mensagens
git checkout main            # versao estavel (tudo mesclado)
cd Experimental
npm install                  # baixa o Chromium do Puppeteer (uns minutos)

2.2 Criar o .env a partir do modelo

Copie o modelo e preencha com os dados da ficha da unidade. É aqui que a unidade ganha a própria identidade — sem tocar em código.

servidor
cp .env.example .env
nano .env                    # preencha; salve com Ctrl+O, Enter, Ctrl+X
Os campos que mudam por unidade
STUDIO_NOMENome do Studio como aparece para a aluna. Ex.: Studio SlimFit Jardim Goiás.
EVO_URLUse https://evo5.w12app.com.br (o login acontece no evo5; o domínio seguro é capturado sozinho).
EVO_EMAIL / EVO_PASSWORDLogin do EVO da unidade.
EVO_EXPERIMENTAL_PATHTroque o número da filial no caminho pelo da unidade.
HEADLESSDeixe false — a instalação roda com Xvfb (tela virtual).
GRUPO_EQUIPENome exato do grupo da equipe no WhatsApp.
SHEETS_ID / SHEETS_ABA / GOOGLE_SA_KEYPlanilha de aniversários (ver passo 2.4).
NTFY_TOPICTópico exclusivo de alertas da unidade (nome secreto).
AUDIO_MAPJSON professora→arquivo de áudio (ver passo 2.3).
FORM_OUTBOX_TOKENToken secreto — o mesmo valor aqui e no formulário na Render.
O .env nunca vai para o GitHub (está no .gitignore). Ele fica só no servidor.

2.3 Colocar os áudios das professoras

Coloque os arquivos de áudio na pasta audios/ e ligue cada professora ao seu arquivo no AUDIO_MAP do .env. A chave é o nome da professora como aparece no EVO (minúsculo).

no seu PC → servidor
# envie os audios do seu PC para o servidor do cliente
scp *.ogg root@IP-DO-CLIENTE:~/SF-Chat_Experimental-Mensagens/Experimental/audios/

# no .env, mapeie professora -> arquivo (sem extensao):
# AUDIO_MAP={"ana":"A-Ana-Pos","carla":"A-Carla-Pos"}
Formato do áudio: nota de voz em .ogg (Opus). Se o cliente mandar MP3, converta antes com o mesmo comando que usamos na sua unidade (remove metadados que travam a reprodução).

2.4 Chave do Google + compartilhar a planilha

Só se a unidade usar a planilha de aniversários. Envie a chave da conta de serviço e compartilhe a planilha com o e-mail dela.

no seu PC → servidor
# envie a chave JSON da conta de servico
scp google-sa.json root@IP-DO-CLIENTE:~/SF-Chat_Experimental-Mensagens/Experimental/
Abra a planilha do cliente → Compartilhar → cole o e-mail da conta de serviço (está dentro do google-sa.json, campo client_email) como Editor. Sem isso, o robô lê mas não escreve.
Fase 3

Conectar e testar

3.1 Escanear o QR do WhatsApp da unidade

Rode a conexão inicial. Um QR aparece no terminal — quem estiver com o celular do Studio escaneia.

servidor
cd ~/SF-Chat_Experimental-Mensagens/Experimental
xvfb-run -a node src/run-now.js whatsapp
No celular do Studio: WhatsApp → Aparelhos conectados → Conectar um aparelho e aponte para o QR no terminal. Conectou? A sessão fica salva. Encerre com Ctrl+C.

3.2 Confirmar a linha dentro do grupo da equipe

Garanta que a linha do Studio (a que você acabou de conectar) está dentro do grupo da equipe — senão os avisos internos não saem. Confira também que o nome do grupo no .env bate exatamente.

3.3 Testar sem e com envio

servidor
# 1) so leitura do EVO (nao envia nada)
xvfb-run -a node src/run-now.js scrape

# 2) uma mensagem de teste para um numero seu
xvfb-run -a node src/run-now.js whatsapp 5562XXXXXXXXX 08:00 Teste

# 3) o job da manha inteiro, agora (envia de verdade!)
xvfb-run -a node src/run-now.js morning
Confirme: login no EVO ok, as experimentais aparecem na listagem, e a mensagem de teste chega no WhatsApp.

3.4 Configurar os alertas (ntfy)

O cliente instala o app ntfy (grátis) e se inscreve no tópico que você definiu no .env (NTFY_TOPIC). Faça um alerta de teste na frente dele.

servidor
# dispara um alerta de teste no topico da unidade
curl -d "Instalacao concluida — teste de alerta" ntfy.sh/SEU_NTFY_TOPIC
Fase 4

Deixar rodando 24/7

4.1 Subir com o PM2 (e voltar sozinho após reboot)

O agendador roda sob o PM2 via o wrapper scheduler-vps.sh (que já embrulha em xvfb-run).

servidor
npm install -g pm2
cd ~/SF-Chat_Experimental-Mensagens/Experimental

pm2 start ./scheduler-vps.sh --name slimfit-exp --interpreter bash --time
pm2 save
pm2 startup systemd -u root --hp /root
# ↑ copie e rode a linha que ele imprimir (registra no boot)

4.2 Verificação final

servidor
pm2 status                       # slimfit-exp = online
timedatectl                      # America/Sao_Paulo
pm2 logs slimfit-exp --lines 50  # sem erros
Deixe rodar até o próximo horário agendado e confirme no pm2 logs que o job disparou.
Fase 5

Formulário na nuvem (opcional)

Se você vender o agendamento online junto, publique o formulário na Render (é separado do servidor). Ele reusa o mesmo pacote de agendamento.

5.1 Criar o serviço na Render

  • ✓Crie um Web Service na Render apontando para o repositório do formulário.
  • ✓Comando de start (já usado): gunicorn app:app --workers 1 --timeout 120.

5.2 Variáveis de ambiente do formulário (na Render)

Environment · Render
EVO_URL / EVO_TOKEN / EVO_DNSAcesso do EVO da unidade para a API de agendamento.
ZEE_CONFIRM_TEMPLATEO texto da confirmação com o nome, endereço, mapa e persona da unidade (é aqui que personaliza a mensagem do formulário — sem editar código).
ZEE_STUDIO_PHONENúmero da recepção que recebe os alertas de turma lotada.
FORM_OUTBOX_TOKENO mesmo token do .env da VPS — é o que liga o formulário ao robô.

5.3 Ligar a ponte formulário → robô

No .env da VPS, aponte FORM_CLOUD_URL para o endereço da Render e use o mesmo FORM_OUTBOX_TOKEN. A ponte roda a cada minuto e puxa as marcações para a fila de envio.

Fase 6

Instagram — boas-vindas (opcional)

O Instagram trata o IP de servidor (datacenter) como robô e bloqueia. Por isso são duas peças, que resolvem coisas diferentes:

  • Cookies = QUEM você é (sessão já logada, sem digitar senha → não dispara 2FA/checkpoint).
  • Proxy residencial/móvel do Brasil = DE ONDE você acessa (um IP de "gente de verdade", não de datacenter).
⚠️ Sem o proxy, mandar DMs do servidor bloqueia a conta (aprendido na prática). Regra de ouro: proxy BR + volume baixo (IG_MAX_DIA=5, subindo aos poucos) + só seguidoras novas.

6.1 Exportar os cookies (no PC do cliente)

Num navegador logado no Instagram do Studio: instale a extensão Cookie-Editor (grátis), abra instagram.com, clique na extensão → Export → Export as JSON (copia para a área de transferência).

6.2 Colar os cookies no servidor

servidor
cd ~/SF-Chat_Experimental-Mensagens/Experimental
nano instagram-cookies.json   # cole o JSON, Ctrl+O, Enter, Ctrl+X

# confere se tem o sessionid
python3 -c "import json;d=json.load(open('instagram-cookies.json'));print(len(d),'cookies; sessionid?',any(c['name']=='sessionid' for c in d))"
Esse arquivo tem o sessionid (acesso à conta) — já está no .gitignore, nunca vai para o GitHub. Fica só no servidor.

6.3 Proxy residencial/móvel (Brasil)

Contrate um proxy móvel do Brasil (ex.: DataImpulse, ~US$ 5) no modo Fixo/sticky. Ele te dá host:porta:usuário:senha. Confirme que sai do Brasil e coloque no .env.

servidor
# testa o proxy (tem que dizer "Brazil")
curl -x "http://USUARIO:SENHA@HOST:PORTA" http://ip-api.com/json ; echo

# no .env:
IG_PROXY=HOST:PORTA
IG_PROXY_USER=USUARIO
IG_PROXY_PASS=SENHA
O robô já baixa sem imagens pelo proxy (economiza dados). 5 GB duram vários meses no nosso volume.

6.4 Testar leitura e um envio

servidor
# 1) so leitura (lista os seguidores)
HEADLESS=true node src/instagram-seguidores.js --user=usuario_do_studio

# 2) um envio de teste para um @ seu
xvfb-run -a node src/instagram-boasvindas.js --teste=seu_instagram
Leu os seguidores e a DM de teste chegou? Então a sessão e o IP estão ok. Se pedir login/checkpoint, os cookies expiraram (reexporte) ou o IP foi bloqueado (aí só proxy residencial resolve).

6.5 Ligar o job

No .env, ligue o Instagram e defina o perfil e o limite diário (o IG_PROXY já foi posto no 6.3). O job roda sozinho às 07:00 e só dá boas-vindas a quem passou a seguir.

.env
IG_ENABLED=true
IG_USERNAME=usuario_do_studio
IG_MAX_DIA=5
Reinicie com pm2 restart slimfit-exp. Os cookies expiram com o tempo — quando isso acontecer, o alerta no ntfy avisa e é só reexportar. Depois de ter o painel (Fase 7), dá para reimportar os cookies pela aba Instagram (cola o JSON), sem scp nem SSH — e testar com um DM.
Depois de instalado o painel (Fase 7), o liga/desliga e o limite/dia passam a ser ajustáveis na aba Instagram — sem mexer no .env nem reiniciar (fica em data/instagram-config.json; o .env vira só o padrão inicial).
Fase 7

Painel do Studio (opcional)

Uma tela com login por usuário e as abas: 📈 Formulário (funil do formulário: acessos, agendamentos, conversão e o gerador de links por origem), 💬 WhatsApp — com Configuração (conexão/QR e desconectar, textos + hora/dias de cada envio), Agendamento (mensagens pontuais) e Log (o que o robô enviou no dia) —, 📸 Instagram (liga/pausa, limite/dia, mensagem e horário das boas-vindas), 🤖 SoFIA — com Configuração, Conversas (ler/responder e assumir), Contatos (CRM com tags, Interações e Automação por tag) e Campanhas (envio em massa por tag; ver Fase 9) — e 👤 Perfis (só o admin: cria usuários e define quais telas cada um vê). Os textos gravam em data/mensagens.json/data/horarios.json e valem no próximo envio sem reiniciar (só mudança de horário reinicia o robô).

7.1 Definir login e subir o painel

Defina o admin (usuário e senha forte) no .env e suba o painel sob o PM2. O login é por formulário (cookie de sessão); o admin do .env é o super-usuário — entra sempre, vê tudo e cria os demais usuários na aba Perfis. Ele escuta só no localhost (o acesso externo vem pelo HTTPS do passo 7.3).

servidor
# no .env (senha longa, com letras e numeros):
# PAINEL_USER=dono   PAINEL_SENHA=uma-senha-bem-forte   PAINEL_PORT=8080
cd ~/SF-Chat_Experimental-Mensagens/Experimental
pm2 start src/painel-mensagens.js --name slimfit-painel --time
pm2 save
curl -s http://127.0.0.1:8080/login | head -c 60   # deve vir HTML da tela de login
Trocou a senha do admin depois? Aplique com pm2 restart slimfit-painel --update-env. Para outros usuários (recepção, etc.), entre como admin → aba 👤 Perfis → crie o usuário com senha e marque só as telas que ele pode ver (ex.: só Conversas da SoFIA). Vale na hora, sem reiniciar; as senhas ficam com hash em data/usuarios.json (fora do Git).

7.2 Subdomínio grátis (DuckDNS)

Sem precisar comprar domínio: crie um subdomínio grátis apontando para o IP da VPS.

  • ✓Em duckdns.org (login com Google), crie um domínio, ex.: painel-unidade → painel-unidade.duckdns.org.
  • ✓No campo current ip, coloque o IPv4 da VPS — pegue com curl -s -4 ifconfig.me (não use o IP do seu PC).
  • ✓Confira que bateu: getent hosts painel-unidade.duckdns.org deve mostrar o mesmo IPv4.

7.3 HTTPS automático com o Caddy

O Caddy emite o certificado (Let's Encrypt) sozinho e encaminha o subdomínio para o painel no localhost.

servidor
# instala o Caddy
apt install -y debian-keyring debian-archive-keyring apt-transport-https curl
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | tee /etc/apt/sources.list.d/caddy-stable.list
apt update && apt install -y caddy

# /etc/caddy/Caddyfile  (troque pelo seu subdominio):
# painel-unidade.duckdns.org {
#     reverse_proxy 127.0.0.1:8080
# }
systemctl reload caddy

7.4 Abrir portas e acessar

servidor
ufw allow 80
ufw allow 443
# tambem libere 80 e 443 no firewall do painel da Hostinger (se houver)
curl -sI https://painel-unidade.duckdns.org | head -3   # HTTP/2 401 = ok (pede login)
!

Só publique com senha forte e HTTPS

O painel fica na internet: use uma senha longa (não uma data/PIN) e nunca exponha a porta 8080 direto — sempre atrás do Caddy. Se o certificado não sair, quase sempre é a porta 80 bloqueada no firewall da Hostinger (o Let's Encrypt precisa dela). Diagnóstico: journalctl -u caddy --no-pager | tail -25.

Pronto: abra https://painel-unidade.duckdns.org no celular ou PC, faça login e edite. As mudanças valem no próximo envio.

7.5 Envios agendados (aba "Agendar envios")

A segunda aba do painel agenda mensagens pontuais. O robô dispara os pendentes do dia às 10:45 (manhã) e 15:45 (tarde) — já ligados no scheduler. Se houver várias no mesmo turno, envia uma de cada vez, com intervalo aleatório entre elas (padrão 20-40s, ajustável no .env).

.env (opcional) · intervalo entre envios agendados
AGENDADOS_INTERVALO_MINSegundos mínimos entre um envio e o próximo (padrão 20).
AGENDADOS_INTERVALO_MAXSegundos máximos (padrão 40). O robô sorteia um valor nessa faixa.
Guardado em data/agendamentos.json (+ pasta data/agendamentos-fotos/). Teste manual: pm2 stop slimfit-exp → xvfb-run -a node src/enviar-agendados.js --turno=tarde --enviar → pm2 start slimfit-exp (a conexão do WhatsApp é única, então pare o robô antes de rodar o script na mão).

7.6 Abas Hoje, Instagram e teste de mensagem

Hoje mostra os envios do dia (total, enviados, falhas e por tipo) lidos de data/atividade.json — sem precisar de pm2 logs. Na aba Mensagens, cada texto tem Pré-visualizar (como a aluna vê) e Enviar teste (dispara de verdade para um número que você informa; o painel grava o pedido em data/teste-envio.json e o robô, que tem a sessão, envia). A aba Instagram concentra tudo do IG: ligar/pausar (sem reiniciar), limite por dia, a mensagem e o horário — o liga/desliga e o limite ficam em data/instagram-config.json. Ali também dá para reimportar os cookies (cole o JSON exportado do navegador — evita o scp dos passos 6.1/6.2) e enviar um DM de teste para um @usuário: se o DM sai, o cookie está válido; se não, avisa para reimportar.

Nada disso reinicia o robô, exceto salvar horários (o painel roda pm2 restart slimfit-exp por você). Qualquer mensagem tem a opção Enviar com foto: o flyer fica em data/mensagens-fotos/ e é enviado como legenda junto do texto (nas de grupo, mantendo a @menção).

7.7 Indicadores do formulário (aba "Indicadores")

Funil do formulário sem SSH: pessoas (visitantes únicos, por cookie — vários F5 da mesma pessoa contam como 1), aberturas (acessos), agendamentos e a conversão por pessoa, por período, com horários/dias de pico e horários de aula mais escolhidos. Robôs de pré-visualização de link (facebookexternalhit, WhatsApp, etc.) são filtrados por User-Agent e não contam. O formulário (Render) registra os eventos; o robô puxa a cada 2 min (reusa FORM_CLOUD_URL + FORM_OUTBOX_TOKEN, os mesmos da ponte de confirmações) e grava em data/indicadores.json — dia/hora carimbados no fuso de São Paulo no VPS.

Para saber a origem dos acessos, use um link etiquetado por canal: …/?origem=instagram, …/?origem=whatsapp, …/?origem=ads. Sem etiqueta, o acesso entra como “(sem etiqueta)”. Os números começam a contar a partir da instalação (não há histórico retroativo).
Fase 8

Vigia e backup (cron)

Dois scripts leves rodados pelo cron do sistema (fora do PM2): um vigia que avisa no ntfy se o robô/painel caírem — o caso que nada mais pega, porque um processo morto não consegue se avisar — e um backup diário da pasta data/ (suas edições do painel, que só vivem na VPS).

8.1 Agendar no crontab

Descubra os caminhos com which node e which pm2 e use-os. Depois crontab -e e cole:

crontab -e
# deixa o pm2 achavel pelo cron (use a pasta do 'which pm2')
PATH=/usr/local/bin:/usr/bin:/bin

# vigia a cada 5 min — avisa se o robo/painel cair (e quando voltar)
*/5 * * * * cd ~/SF-Chat_Experimental-Mensagens/Experimental && /usr/bin/node src/watchdog.js >> logs/watchdog.log 2>&1

# backup diario da pasta data/ as 03:10 (guarda as ultimas 14 copias)
10 3 * * * cd ~/SF-Chat_Experimental-Mensagens/Experimental && /usr/bin/node src/backup-dados.js >> logs/backup.log 2>&1
Teste na hora: node src/backup-dados.js (cria backups/data-….tar.gz) e node src/watchdog.js (deve dizer “✅ tudo ok”). O vigia usa o mesmo NTFY_TOPIC dos alertas. Ajustes opcionais no .env: BACKUP_MANTER (nº de cópias, padrão 14), WATCHDOG_WA_MIN (minutos de WhatsApp caído antes de avisar, padrão 30).
Fase 9

🤖 Sofia — chatbot com IA (opcional)

A Sofia atende as leads no WhatsApp e agenda a aula experimental sozinha, usando uma IA da Anthropic (Claude). Ela roda em um processo próprio (sofia-listener) e usa um número de WhatsApp exclusivo, diferente do robô de mensagens. Tudo o que ela fala e faz é editável pela aba 🤖 Sofia do painel.

9.1 Instalar as dependências

O código da Sofia fica na pasta ChatBot/ do mesmo repositório.

servidor
cd ~/SF-Chat_Experimental-Mensagens/ChatBot
npm install

9.2 Configurar o .env da Sofia

No .env dentro de ChatBot/:

ChatBot/.env
ANTHROPIC_API_KEYChave da IA (Claude). É o que tem custo por conversa — separado do servidor.
SOFIA_TOKENSenha compartilhada com o formulário (Render). Precisa ser idêntica ao SOFIA_TOKEN do formulário — é o que autoriza a Sofia a agendar no EVO.
SOFIA_BOOK_URLEndpoint do formulário que agenda (padrão: o form no Render, …/api/book-sofia). Normalmente não precisa mexer.
NTFY_TOPICOpcional — mesmo tópico dos alertas do robô. Com ele, a SoFIA avisa no celular quando a sessão dela cair (precisa de QR), quando travar (a verificação de conexão reinicia sozinha) e quando uma campanha auto-pausa por falhas.
CHROMIUM_PATHOpcional — caminho do Chromium, se o padrão não for encontrado (mesmo do robô).
O ritmo de digitação, a pausa do atendimento humano e o roteiro dela não ficam no .env — são editáveis no painel (aba 🤖 Sofia) e valem na hora, sem reiniciar.

9.3 Subir sob o PM2

Assim ela sobe junto com o servidor e não morre ao fechar o terminal.

servidor
cd ~/SF-Chat_Experimental-Mensagens/ChatBot
pm2 start npm --name sofia-listener -- run listener
pm2 save
pm2 logs sofia-listener        # espere aparecer "PRONTA"
Entre autenticada e PRONTA a conexão leva de 20 a 60 s (carrega as conversas) — normal.

9.4 Conectar o WhatsApp próprio da Sofia

Na primeira vez (ou quando a sessão cair), a Sofia mostra um QR. Escaneie com o celular do número dela (não o do robô): no painel, aba 🤖 Sofia → o QR aparece e atualiza sozinho; ou no terminal, pelo pm2 logs sofia-listener.

!

O QR é um login — trate como senha

O QR conecta a conta de WhatsApp da Sofia. Ele é gerado localmente (nunca enviado para sites de QR externos). Não compartilhe o print. A sessão fica guardada em ChatBot/.wwebjs_auth (fora do Git).

9.5 Ajustar tudo pelo painel

Na aba 🤖 SoFIA do painel (sub-aba Configuração) você edita o roteiro (o que ela fala), liga/desliga, e ajusta num grid: tempo de sessão (memória), agrupar mensagens (espera alguns segundos e responde tudo junto), verificação de conexão (health-check — reinicia sozinha se travar), máx. de experimentais por turma, pausa ao responder pelo celular, o ritmo de digitação e as imagens (grade/preços); e pode desconectar o WhatsApp dela por ali. As outras sub-abas: Conversas (ler/responder e assumir o controle de uma conversa), Contatos (CRM: importar CSV, etiquetar, Interações — histórico com resumo por atendimento — e Automação por tag — gatilhos que etiquetam e avisam sozinhos) e Campanhas (envio em massa por tag, com variações da IA, limites, foto e {nome}). Tudo vale na hora, sem reiniciar.

O roteiro e as imagens ficam em ChatBot/sofia-prompt.txt, sofia-extracao.txt e sofia-midias.txt — editados pelo painel e fora do Git (o conteúdo base fica nos *.default.txt versionados; se o arquivo vivo sumir, é recriado dele). Por isso o git pull nunca conflita com o que você editou no painel.
Arquivos de execução da SoFIA (todos em ChatBot/, gitignored — só vivem na VPS): sofia-conversas.json (inbox), sofia-historico.json (interações), sofia-humano.json (controle humano), campanhas.json, e as pontes com o painel — sofia-agendou.jsonl/sofia-eventos.jsonl/sofia-avisos.jsonl (automações) e os ajustes sofia-sessao-horas.txt, sofia-health-min.txt, sofia-agrupar-seg.txt. As tags/automações e os canais de origem ficam no lado do painel, em data/tags-config.json e data/origens.json. Após um git pull que mexa na SoFIA, reinicie: pm2 restart sofia-listener --update-env.
